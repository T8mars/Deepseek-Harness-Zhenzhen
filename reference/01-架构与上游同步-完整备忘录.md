## 1. 结论摘要

### 1.1 推荐方案（一句话）

**混合形态，A 层先行、B 层按需**：

- **A 层 = 下游发行（不 fork）**：我们的仓库只放自己的 npm 包（一个配置 bundle + 客户端插件 + 服务端插件 + SKILL 包），装进用户已经装好的官方 Desktop 的 `desktop` profile。上游代码一行不改，靠 Cordis 的 bundle/profile 分层覆盖配置、禁用 DeepSeek 绑定行、注入 UI。
- **B 层 = 自有安装包（可选，M5）**：只有在需要"换产品名/图标/更新源/欢迎页密钥写入目标/钉死上游版本"时才做。做法不是 fork 合并，而是"钉死上游标签 + 补丁队列 + 文件覆盖"，在 GitHub 托管 runner 上自己出包。
- **同步机制**：定时探测上游新标签 → 自动开 PR → 契约测试把"我们依赖的上游假设"逐条断言 → 通过才放行。永远不合并上游分支。

### 1.3 最大风险 Top 5

1. **官方 Desktop 会自动更新，A 层无法钉版本**。官方打包应用启动时检查固定的 Nightly 通道〔src: apps/desktop/README.md:272〕，更新源固定在 `https://download.deepseek.com`〔src: apps/desktop/scripts/desktop-auto-update-environment.mjs〕。上游一旦升到我们 `engines.dsh` 范围之外，不兼容的 bundle 会被静默跳过并列入 `skippedBundles`〔src: packages/boot/app-boot/README.md:52〕，默认模型悄悄退回 DeepSeek。缓解：宽范围 + 快速 CI + 版本漂移告警；根治：B 层。
2. **Seedance 的关键行为文档里没写**：流式 `usage`、`reasoning_content` 字段与回传、思考开关参数、工具调用流格式、`/v1/models`。全部【待实测:T-01..T-12】，其中 `reasoning_content` 回传不对会直接 400 或丢上下文。
3. **官方欢迎页与 DeepSeek 密钥强耦合**：`save(apiKey)` 只往 `llm-deepseek` 命名空间的 `apiKeyEnv` 引用写密钥〔src: apps/desktop/src/welcome-backend.ts:~75-150〕。A 层要靠环境变量或预置凭据绕过，B 层才能改。
4. **DeepSeek 绑定的出站行默认开启**：会话日志上传、OTel 反馈、桌面产品分析（`product-analytics.enabled` 默认 `true`，没有用户可见开关）〔src: packages/client/product-analytics/README.md:24；packages/bundle/base/cordis.patch.yml；packages/bundle/web-app/cordis.patch.yml:46-62〕。必须在 bundle 里禁用，并用抓包契约测试守住（T-16、T-21）。
5. **上游节奏快且会破坏兼容**：`dsh-v*` 标签 32 个，其中 v0.2.1-alpha.1 一个版本就带 22 篇升级指南〔ext: git ls-remote；src: docs/upgrade-guide/v0.2.1-alpha.1/〕；README 明示可能有破坏性变更；上游不接受外部 PR〔src: CONTRIBUTING.md〕。我们没有"反馈修复"通道，只能靠契约测试尽早发现。

### 3.1 三种形态对比

| 维度 | Fork 上游主干 | 纯下游发行（不 fork） | 混合（推荐） |

### 3.6 为什么不直接 fork（再强调三点）

1. 上游预发布节奏约每 1–2 天一个标签，fork 的合并成本随时间线性上升，且上游不收 PR，我们的修改永远不会被吸收。

3. B 层若必须改源码，也用"补丁队列 + 钉死标签"而不是长期分支：每次升级是"重放 N 个小补丁并跑测试"，而不是"解 N 百行冲突"。补丁预算见 §5.5。

### 4.4 最大的结构性陷阱：patch 替换整行 config

`llm-pi-ai` 行的 `providers` 是整个配置面，而 Models 页写的也是这一段，写到 **profile 层（第 4 层）**〔src: docs/user/guide/providers.md:11-13,52；packages/bundle/base/cordis.patch.yml 注释〕。按 F-05，第 4 层的 `llm-pi-ai` 会**整体替换**我们第 3 层的 `llm-pi-ai`。于是：

```
 第3层 (我们):  providers = { seedance }
 用户在 Models 页新增一个自定义 provider foo, 保存
 第4层 (profile): llm-pi-ai.config.providers = { ??? }
        若编辑器以"生效配置"为底稿 -> { seedance, foo }       => 安然无恙
        若编辑器只写用户新增     -> { foo }                   => seedance 路由消失, 默认模型指向不存在的路由
```

编辑器到底怎么写：【待实测:T-14】。缓解措施按成本递增：

1. 契约测试 C2：用"模拟 Models 页保存"的方式写第 4 层，再 `--dump-config`，断言 `seedance` 仍在。
2. 守卫插件 `dsh-zhen-guard`【拟定】：启动时检查 `seedance` 路由是否存在；缺失就在界面给一条横幅 + "恢复默认"按钮（经 `ctx.configEditor` 服务写回，该服务在上游服务清单中：`ctx.configEditor` "Profile configuration edits"〔src: docs/capability-seams.md〕；具体 API 未读，T-14b）。
3. 备选设计 A2：把 Seedance 放在**第二个** `dsh-llm-pi-ai` 行（独立 `id`），避免与用户编辑的行互相覆盖。风险：两个 pi-ai 实例共用 `llm-pi-ai` 设置命名空间与路由所有权规则（README 说另一适配器已占有的路由会被保留〔src: packages/llm/llm-pi-ai/README.md:111〕），是否可行【待实测:T-14b】。

### 5.5 补丁维护策略（仅 B 层）

- **补丁队列**：`patches/NNNN-<主题>.patch`，由 `git format-patch` 生成，基底 = `upstream/` 子模块指向的标签。每个补丁头带四行元数据：`Upstream-Anchor:`（文件#符号）、`Why:`、`Test:`、`Removal-condition:`。
- **应用**：CI 中 `git -C upstream checkout <标签> && git -C upstream am --3way ../patches/*.patch`；失败则自动开 issue，附 `git range-diff` 与失败补丁。
- **补丁预算**：≤ 4 个行级补丁、合计 ≤ 300 行变更（不含整文件/资源覆盖）；超出需写决策记录。
- **覆盖文件**：`overlay/` 下每个文件记录它覆盖的上游文件的 blob 哈希；上游该文件变化即告警——整文件覆盖最容易静默落后。
- **不长期持有分支**：每次升级都是"换标签、重放补丁、跑测试"，不是"解冲突"。

### 5.6 GitHub Actions 设计

上游的 CI 用企业/自托管 runner 和 EV 硬件令牌签名（F-16），**不可复用**；我们全部用 GitHub 托管 runner。

| 工作流 | 触发 | 作用 |
|---|---|---|
| W1 `ci.yml` | PR、push | 安装 → lint → 构建 → 契约测试 C1–C4、C6、C7（离线）→ 打包 tgz → 许可证扫描 |
| W2 `upstream-watch.yml` | cron 每 6 小时 + 手动 | `git ls-remote --tags` 取最大 `dsh-v*`（SemVer 排序，含预发布）；`npm view @deepseek-ai/dsh-base dist-tags.next`；与 `UPSTREAM.lock.json` 比较；有新就调用 W3 |
| W3 `upstream-sync.yml` | 被 W2 调用、手动 | 开分支 `sync/dsh-v<X>`；更新 `UPSTREAM.lock.json`（candidate）；列出新增升级指南；跑全量 C1–C10；开 PR，正文含受影响的行/槽位/指南与契约结果；全绿贴 `canary-ready`，有红贴 `needs-attention` 并建 issue |

### 5.7 版本方案

- **我们的包**：独立 SemVer `0.<minor>.<patch>`，不跟随上游号；预发布通道用 `-canary.N`。
- **`UPSTREAM.lock.json`**（格式【拟定】）：`{ upstream: { repo, tag, commit, npm }, channel, verifiedAt, guidesReviewed: [...] }`，由 W3 维护，人工只在 ack 时改 `guidesReviewed`。
- **`engines.dsh`**：由 W4 根据 `compat.json` 自动写入"已验证区间"。上游预发布参与匹配（F-06），区间必须显式覆盖预发布；canary 通道区间宽、stable 通道窄。A 层受风险 #1 影响，区间过窄会让 bundle 被官方自动更新静默淘汰，过宽则可能在未验证版本上运行——这是个取舍，建议 canary 宽 / stable 窄，并让守卫插件（§4.4）在检测到未验证版本时给出横幅。
- **B 层安装包版本**：上游规定一次构建的版本只能是产品版本本身，或 `<产品预发布字段>.<日期>.<序号>` / `<日期>.<run>.<attempt>` 形式，且**不能带构建元数据**（`+…`），因为 `electron-updater` 用 `semver.gt` 比较〔src: apps/desktop/scripts/desktop-build-version.mjs:40-100〕。所以 B 层安装包版本形如 `0.2.1-rc.2.20261101.1`，我们自己的语义版本放进 `extraMetadata` 和"关于"页，不参与更新比较；除非改这段校验（会多一个补丁，不建议）。
- **GitHub Release 标签**：`v<我们的版本>`；上游版本放进 `compat.json` 与 Release 说明表。

### 5.9 回滚

| 层级 | 场景 | 做法 | 备注 |
|---|---|---|---|
| L1 | 我们的 bundle/插件有问题 | `dsh plugin --profile desktop add <上一版 tgz>`，或 Plugin Manager 降级；极端情况 `dsh plugin remove` 立刻回到官方默认 | 最快、最常用 |

### 7.5 预设：新工具与技能如何进入 Web 会话

事实：

- Web 的 Agent 预设就是一行 `@deepseek-ai/dsh-agent-preset`，`config.plugins` 是**每个 Agent 的子插件列表**（工具、技能、persona 都在里面）；`agent-preset-registry` 的 `default` 决定新会话用哪个预设；用户保存的默认（`selectedDefault`）优先于部署的 `default`〔src: packages/bundle/web-app/presets/standard.patch.yml；packages/preset/agent-preset-registry/README.md〕。
- 文档化的做法：**新增预设或覆盖预设都是 bundle patch——`insert` 一行 `dsh-agent-preset`，或按该行 id 打补丁**〔src: packages/preset/agent-preset-registry/README.md〕。
- 覆盖会重述整份 `plugins` 列表，上游预设后续新增的插件不会自动并入（静默漂移）〔src: packages/preset/agent-preset/skills/editing-cordis-compositions/SKILL.md〕。
- `docs/architecture.md:27` 声称存在 `preset` 类 patch 键，但我在 `packages/boot`、`vendor/include` 中**没找到实现**，只在测试夹具 `scripts/verify-default-product-isolation.spec.ts:160` 看到示例——【未核实】，不要依赖。

做法（推荐）：

1. **不覆盖上游预设，新增我们自己的**：`dsh-zhen-bundle` 里 `insert` 一行 `preset-zhen`（`config.id: zhen`），其 `plugins` 由 `scripts/gen-presets.mjs` 从上游 `presets/standard.patch.yml` 机器生成：保留上游全部插件 + 我们的 persona + `rag_search`/`rag_open` + 技能根配置；再覆盖 `agent-preset-registry` 行，`default: zhen`。
2. **契约 C7** 在每次同步时重新生成并 diff，上游预设变了就红，由人决定是否并入。
3. 根级（预设之外）注册的工具对 Web Agent 是否可见：【待实测:T-19】。MCP 行写在根级（F-22 的示例）。

### 7.6 Skill 目录约定与分发

约定（F-21）：`<根>/<name>/SKILL.md`；frontmatter 有 `name`、`description`，另有 `disable-model-invocation`、`user-invocable` 两个布尔键；正文每次加载重读，改正文无需版本或缓存失效。根与优先级：

```
 100 <项目>/.dsh/skills          200 <项目>/.agents/skills        300 customSkillDirs
 400 $DSH_HOME/skills            500 $DSH_AGENTS_HOME/skills      600 bundledSkillDir
 (数字小者优先)                    (~/.agents 与其他 Agent 工具共享)  (最低, 适合放"可被用户覆盖"的默认技能)
```

分发方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| **K0 专用 provider（推荐）** | `dsh-zhen-skills` 作为根级插件，用 `ctx.skills.registerProvider(...)` 注册一个 provider，`list()` 返回带 `bundled` 排名（600）的候选，`resourceBase` 指向包内资源目录。上游有先例：实验插件 `dsh-skill-badge` 就是这样发布打包技能的；文档明说"部署通过配置的 bundled 根或专用 provider 提供打包技能" | 不拷贝文件、不需要路径表达式；排名最低，用户在预设层/用户目录里的同名技能会遮蔽我们的（"更近的层整体胜出"）；全局层注册对所有预设可见。来源：`docs/subsystems/skills.md:77,79`；`packages/skill/skill/README.md:52,84,140` |
| K1 `bundledSkillDir` | 在 `skill-filesystem` 配置里指向包内目录（排名 600） | 干净，但"包内目录的绝对路径"如何在 patch 里表达【待实测:T-18】 |
| K2 受控目录 | `dsh-zhen-skills` 启动时把包内 `skills/*` 同步到 `$DSH_HOME/zhen/skills/`（按内容哈希幂等，只管理带 `zhen-` 前缀的目录），预设里的 `skill-filesystem` 配 `customSkillDirs: [!!js dshHomePath('zhen','skills')]` | K0 不可行时的退路；路径表达式有先例（`dshHomePath` 在 base patch 已用）；排名 300 高于用户目录 |
| K3 直接写 `$DSH_HOME/skills` | 安装脚本复制 | 用户会手改，升级冲突 |
| K4 项目级 `.dsh/skills`、`.agents/skills` | 随某个画布项目走的专用技能 | 仅用于项目专属技能 |
| K5 `~/.agents/skills` | 与其他 Agent 工具共享 | 02 号备忘录建议"一份 SKILL.md 两边用"；放这里会影响别的工具，慎用 |

注意：预设里也有 `skill-filesystem` 与 `tool-skill`（`standard.patch.yml`），而注册表是"全局层 + 每个预设层"分层的——宿主行/根级插件注册进全局层，预设内插件注册进该预设的层；读取时合并全局层与观察者作用域链，**最近的层整体胜出**，同层内按排名、provider 注册顺序决定〔src: packages/skill/skill/README.md:84〕。所以走 K0 时我们的 provider 在全局层，对所有预设可见；走 K1/K2 时配置要写进我们生成的 `preset-zhen` 里才对 Web 会话生效（T-18/T-19）。K0 的 `ctx.skills.registerProvider` 签名与 `list()`/`get()` 契约以 `docs/subsystems/skills.md` 为准，我只读了概述【未核实细节】。技能命名前缀、frontmatter 交集字段、`catalog.json` 旁路文件等细节以 02 §5 为准。

## 11. 给实现 AGENT 的工作规则

1. **先 M0，且先做 §10.1 的实测再写配置**。不要把 §4.3 的片段当成最终值。
2. 任何改动先问：能不能放进"bundle 行 / 客户端插件 / 服务端插件 / SKILL / MCP"？能就不要碰上游。
3. 不碰 §5.3 的清单。需要读写会话日志、凭据文件、profile 私有文件时，改用对应的服务或 CLI。
4. 所有对上游的假设必须有契约测试；写新代码时同步在 `contracts/` 加一条。
5. 对 `llm-pi-ai` 行、`agent-preset-registry` 行等"整行替换"的覆盖，必须在补丁文件里重述该行的全部配置，并在注释里写明上游来源与版本。
6. 凭据只经 `ctx.credentials`，日志里不打印密钥、不打印会话全文；CI 的 `SEEDANCE_API_KEY` 只给 W6。
7. 美术资源不由我们生成或描述；只提供加载位置和尺寸规范，素材由用户放入 `packages/dsh-zhen-client-brand/assets/`【拟定】。
8. 默认禁用所有指向 DeepSeek 的上报；如需开启，必须在界面里明示并取得用户同意。
9. 每个里程碑结束写一页 `docs/decisions/NNNN-*.md`，记录偏离本备忘录之处与原因。
10. 不向上游提 PR；上游行为问题记录在 `docs/upstream-assumptions.md`，由契约测试守着。
