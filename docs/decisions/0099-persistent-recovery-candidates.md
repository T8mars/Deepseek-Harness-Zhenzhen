# 0099 · 重启后继续管理恢复候选

0098 的候选基线随最多16项内存任务保存，退出应用后便无法继续复核。本次增加自有候选记录库和创作空间历史列表，并完成一次分阶段的实际已发布SDK环境备份/恢复验证。完整应用恢复和激活仍未完成。

## 实现

- Host启动时固定自有 `recovery-candidates.sqlite` 路径；冷读取不创建文件或目录。每项记录保存原任务ID、候选路径、创建时间、摘要与原文件基线，不含密码、文件内容、会话或凭据。SQLite事务保持其他Host的记录，首次建库独占发布；未知schema和异常记录拒绝，不迁移或重写。
- 初始目录别名解析后固定归属；后续目录别名改指、暖库文件替换或文件链接拒绝继承原身份。分页每页20项，没有沿用内存16项上限。重启和内存任务淘汰后仍可按原ID查询；创建时记录与当前文件复核继续分开。
- 从持久记录复核前，先有界读取既知组合回执并确认候选角色、目录和组件身份，再进行原有文件扫描；回执不能替代自有库内的原始基线。链接目标不遍历。读取、注册与其他备份任务保持互斥，卸载取消读取。
- 恢复文件生成后保存记录失败，保留候选路径和基线，显示「重试保存记录」。重试先复核同一候选，再保存记录，不解密重做、不重复恢复。移除记录可重复调用，只删自有索引和内存引用，保留全部候选及备份字节。
- 新增三个严格Owner Remote，十一项备份接口均拒绝匿名；没有新增Agent工具。明确的Host忙碌拒绝与丢回执区分，未被接受的请求不会留下假待查询编号。历史列表、翻页、刷新、移除和注册处理重复点击、旧API、页码/任务变化与迟到响应。
