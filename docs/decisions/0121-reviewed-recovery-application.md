# 0121 · 审阅后打开独立恢复应用

完整示例此前能够还原、校验并读取会话与附件，但工作区、会话控制器和工作区控制器被恢复配方暂停，页面就绪不代表完整应用可用。现在在原有恢复候选中加入明确的程序来源审阅和“确认并打开恢复应用”，沿用已经准备的独立应用副本。

Host 根据保留的原校验记录重新检查文件，通过固定已发布 SDK 的公开 profile、overlay 和运行时解析接口读取完整树。程序来源依据实际目录，包含公开解析表刻意省略的 bundle 自身；不按包名前缀授予信任。原本停用的工作区不会提升，定时任务和指定上报仍暂停，默认工具权限保持只读、逐次询问。程序尚未完整还原时拒绝启动。

明确批准后，沿用现有环境装配的标准 Node 链接和公开 manifest writer，将自有数据快照 bundle 选为同名 profile 的普通基线。它没有依赖或安装脚本，不调用包管理器重建已还原的依赖图，也不改包管理器元数据。原组件、加密备份和 portable overlay 保留，没有复制另一份完整运行环境或修改 SDK 私有 profile 文件。

完整审阅树已包含用户配置层的效果。采用时保留这份公开 `cordis.patch.yml` 的原字节，再用固定版本的公开 `writeFileAtomic` 将新应用的用户层初始化为 `[]`。这样旧插入行和旧权限覆盖不会再叠加到完整快照之上；今后的 ConfigEditor 仍正常保存。原始配置仍在保留记录和原备份中。早期整树 CLI overlay 会使 ConfigEditor 拒绝保存，现仅本机监听和当前自有监视插件使用窄覆盖。

启动使用当前安装的公开 DSH CLI。自有普通插件通过公开 `appReady.onReady` 等待成功启动，再确认会话持久化、附件、工作区及两个控制器、配置编辑器、Web 页面和认证服务实际就绪；原配置包含 DSH-zhen 时还要求其服务就绪。没有 Web 入口的配置会在审阅前拒绝。本机端口随机分配，认证页面只由 Host 在内存中生成并交给系统浏览器。Remote 不返回认证 URL、设置正文或控制密钥。

本机启动授权与一次性请求记录只存于 `ctx.credentials` 的自有 grant。密钥只经瞬时子进程 IPC 初始化；后续状态、显示和关闭通过双向 HMAC 本机通道，带新挑战和重放限制。重复请求不启动第二个进程；状态未知只查询，不按旧 PID 杀进程或自动重开。关闭来源 Host 后可以找回原运行进程。窗口操作绑定 execution，旧按钮不能关闭后来重开的窗口；保留请求历史以拒绝旧请求再次启动。记录上限拒绝继续写入，不丢弃旧请求以换取重放风险。

正常使用会写入这个独立副本，原 seal 不再表示运行后的状态。界面因此隐藏旧候选校验和项目分叉入口，后续在恢复应用中继续设置与备份。再次恢复时剔除旧执行监视插件。技能调用、管理和自动更新仍使用已有的分别审阅入口；旧授权、API 密钥和画布批准不继承。
